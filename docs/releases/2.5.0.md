# landspec 2.5.0

## `/landspec:implement`: a feature's tasks in parallel

`/landspec:implement [feature]` runs every task that can start, each as a background implementer in
its own copy, and drives each one through the independent review, fix rounds, the scan and its PR.
It never merges: you merge, in the printed `ORDER`. It is now the default after `/speckit-tasks`;
`/landspec:next` and `/speckit-implement <task>` still do one task at a time.

### Start every task of a feature at once (user story 1)

- #140 make a task's claim exclusive across clones
- #143 derive every task's state and next step
- #145 `/landspec:implement` runs a feature's tasks in parallel
- #162 say what each waiting task waits for (`REASON=`, and how to free a locked worktree)
- #164 only implementers take `parallel_tasks:` slots, and a task whose tests stay red twice fails
- #167 without `worktree_setup:`, an implementer prepares its copy from the README, or fails with `setup:`

### Dependent tasks start without waiting for a merge (user story 2)

- #141 stack a task on another's reviewed branch
- #142 a stacked task's PR opens as a draft into its parent
- #144 restack stacked branches once a parent merges, and stack one task on another
- #161 a startable task stacks on its one unmerged dependency

### Check the whole feature together (user story 3)

- #146 check all task branches together, against the full suite and the spec
- #148 file the whole-feature check's gaps as tasks, and make `/landspec:implement` the default
- #169 check the whole feature on the base once every task is merged

### A release when the feature is merged (user story 4)

- #149 prepare the release PR when the feature is merged, then tag and publish it
- #150 run the full security audit unattended before the release; a confirmed critical or high holds it
- #163 `audit-record` refuses a commit that is not on origin's base
- #166 `release-plan` reads the tasks from origin's base, as `status` does
- #170 without `release_notes:`, publish the notes from the release PR's body
- #171 the audit runs `/code-review high` and `/security-review`, lists known issues by repository visibility, and names missing scanners

### The default way to implement (user story 5)

- #148 the spec PR's last line and `next.sh` (`RUN=/landspec:implement <feature>`) point to it
- #174 the README's flow image names `/landspec:implement`, with `/landspec:next` for one task

## The independent review

- #138 every review runs in its own copy of the reviewed commit, never in your checkout
- #139 personal data is followed into the helpers that log it
- #168 a function whose failure behavior changes reopens every caller, with how each handles it

## Fixes

- #172 every PR lookup counts only this repository's PRs, never a fork's; only a PR titled exactly `chore(release): X.Y.Z` is a pending release
- #173 spec PRs start from the base, a PR stacked onto a task branch is turned back into a draft, `release-bump` changes one version line per file, and a crashed semgrep is reported `failed`, not `findings`
- #165 the static tests no longer fail of SIGPIPE on long sections
- #123 `/landspec:adopt` wires a project's own mutation harness to `mutate`, scoped to the change

## Known issues

From the audit before this release: 0 critical, 0 high, 1 medium (review gate) and 12 low (business
logic, error reporting, hardening, supply chain). They are tracked for the next release.

## Upgrading

`claude plugin marketplace update landspec && claude plugin update landspec@landspec`, then
restart Claude Code, and run `/landspec:init` in each project so its copy of the scripts is current.

New keys in `landspec-config.yml`, all optional: `parallel_tasks` (4), `feature_rounds` (3),
`implement_model` (the session's) and `worktree_setup` (empty: each implementer prepares its copy
from the README). See docs/reference.md.
